# BingX crypto support in eTape

Research date — November 18, 2026. BingX Spot can supply the three panels most useful for evaluating crypto in eTape: Chart, Time & Sales, and the DOM ladder. A public BTC-USDT connection delivered trades, one-minute candles, and 20-level depth together. The first engineering decision is how eTape represents a fractional base-asset amount from feed to screen. That decision affects all three panels before an order ticket is involved. [BingX API portal](https://bingx-api.github.io/docs-v3/#/en/info)

## What the public API delivered

These observations come from short, unauthenticated production reads. Pair rules are examples from that session and can change.

| eTape use | BingX Spot interface | Observed behavior and implication |
| --- | --- | --- |
| Pair lookup and validation | `GET /openApi/spot/v1/common/symbols?symbol=BTC-USDT` | Returned a price tick of 0.01 USDT, a quantity step of 0.000001 BTC, separate quantity and notional limits, and buy/sell availability. Load all applicable rules per pair. |
| Chart history | `GET /openApi/spot/v2/market/kline` | One-minute and daily rows arrived newest first with separate BTC volume and USDT turnover. Requesting daily bars with `timeZone=0` gave midnight UTC starts. Omitting it gave 16:00 UTC starts. Choose a day boundary explicitly and use it for derived weekly/monthly bars, chart history, and daily comparisons. |
| Tape and live 10-second bars | `BTC-USDT@trade` | A gzip frame contained a single trade object with exchange time, a string ID, price, size, and buyer-maker flag. One print was 0.010479 BTC. The published example describes an array. Decode observed shapes, deduplicate by instrument and trade ID, and bucket by exchange time. Buyer-maker means the seller initiated the trade. |
| Live minute chart | `BTC-USDT@kline_1min` | Received a nested candle with start and end times, OHLC, base volume and quote turnover. REST spells the interval `1m`. Merge updates by bar start so the current REST candle and stream updates cannot double its volume. |
| DOM ladder | `BTC-USDT@depth20` | Received price/quantity strings on both sides. The sampled asks started in descending price order. Normalize bids and asks by price before selecting the best levels. Label the ladder as BingX liquidity. |
| Recovering missed prints | `GET /openApi/market/his/v1/trade` | Returned recent trades and accepted a string `fromId` cursor. Passing the oldest sampled ID returned strictly older trades. Historical IDs were longer than JavaScript's safe integer precision and differed in shape from the live trade ID. Verify the overlap mapping and retention before promising seamless 10-second backfill. |

REST base is `https://open-api.bingx.com`. The three live subscriptions used one connection to `wss://open-api-ws.bingx.com/market`. The adapter needs gzip decoding, heartbeat replies, resubscription and recovery. BingX also documents best bid/ask and rolling 24-hour statistics. The latter can support a watchlist or a later crypto scanner if the UI labels the comparison window. Pace background history separately from foreground reads and account for the shared IP budget. The published limit notice and endpoint references give different levels of detail, so verify the applicable limits before scaling to many pairs. ## Where eTape needs to change

| Area | Current behavior | Proposed handling |
| --- | --- | --- |
| Instrument identity and routing | Symbol entry recognizes US and HK prefixes and adds `US.` to bare input. BingX's spot and perpetual APIs both returned `BTC-USDT`. | Include exchange, product and pair in the instrument key used for subscriptions, cached bars, workspaces and order routes. Preserve existing stock keys. A crypto-only chart should work with OpenD offline. [Symbol input](../ui/src/chrome/symbol.ts) · [History routing](../engine/internal/backfill/backfill.go) |
| Amounts and prices | Ticks, book levels and OHLCV bars use integer volume. The recorder also uses integer quantities. The execution request accepts a floating quantity, but Chart Risk Entry floors the result to whole shares. | Preserve exact fractional quantities across ingestion, recording, wire messages and display. ## Trading and product choice

**Spot** fits a buy/sell ticket with balances per asset. BingX documents limit and market orders, conditional orders, cancellation, client order IDs and private execution reports. A BTC quantity and a USDT spend are different inputs. Track available and locked amounts, partial fills, and the asset charged for fees. Private order REST calls use a timestamp, an API-key header and an HMAC-SHA256 signature. Renew the private stream's listen key and reconcile open orders and fills after reconnect. On a submit timeout, query by client order ID before retrying. eTape's existing 28-character alphanumeric ID fits BingX's documented spot format. [Spot orders](https://github.com/BingX-API/api-ai-skills/blob/main/skills/spot-trade/api-reference.md) · [Authentication](https://github.com/BingX-API/api-ai-skills/blob/main/skills/references/authentication.md) · [Private spot events](https://github.com/BingX-API/api-ai-skills/blob/main/skills/spot-ws-account/api-reference.md) · [eTape order IDs](../engine/internal/exec/orderid.go)

**USDT-margined perpetual futures** fit a workflow that needs leveraged longs and shorts. The public contract lookup returned a distinct BTC-USDT contract with USDT settlement, its own price and quantity precision, and separate flags for opening and closing positions. Charts, tape, book and order triggers should follow that contract's market. Execution additionally needs margin and position modes, leverage, reduce-only behavior, and explicit handling of last price versus mark price. P&L should account for funding and fees. BingX lists demo trading for perpetual futures. Spot demo order coverage and private account behavior were unverified in this research. ## Recommended first milestone

Start with one selectable BingX spot pair, one linked Chart/Tape/DOM workspace, local recording, and order entry disabled for that instrument. If shorting perpetuals is the intended workflow, start with the perpetual market feed instead and verify its streams independently. The shared work on identity, units and calendars applies to either choice.

The first acceptance check is to open BTC-USDT with OpenD disconnected, follow a fractional trade through the tape and a 10-second candle, verify a completed minute against REST, and compare the ladder's best prices with BingX. Repeat across a reconnect and reopen the workspace beside an existing stock chart. Verify weekend and daily boundaries with fixtures. Measure tick-history overlap and flag any unrecoverable gap. After that, add paper execution for the selected product and exercise partial fills, fee currency, restart reconciliation and ambiguous submit outcomes before enabling live routing.
